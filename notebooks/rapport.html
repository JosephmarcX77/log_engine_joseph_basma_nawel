1. Présentation et architecture¶

Le moteur lit des fichiers de logs hétérogènes (JSON, texte brut, connexions), les nettoie, les normalise, les route, agrège des indicateurs de sécurité en une seule passe et applique un moteur de règles configurable. Toutes les étapes sont des itérateurs paresseux : la mémoire ne dépend pas de la taille des fichiers.

def read_multiple_sources(paths: Iterable[Path]) -> Iterator[str]:
    """Enchaîne plusieurs sources en un seul flux grâce à ``yield from``.

    ``yield from read_log_file(path)`` délègue l'itération au sous-générateur :
    chaque ligne est transmise directement au consommateur, sans liste
    intermédiaire. Une source manquante ou illisible est signalée par un
    *warning* puis ignorée : le flux continue avec la source suivante.
    """
    for path in paths:
        try:
            yield from read_log_file(path)
        except LogSourceError as exc:
            logger.warning("%s -> source ignorée", exc)
            continue

build_pipeline compose map(str.strip), filter(None), trois filter(lambda …), map(normalize_record) et map(route_record). Chaque étape est comptée au passage.

def route_entry(entry: object) -> str:
    """Route une entrée selon sa STRUCTURE, uniquement avec ``match-case``.

    Aucun ``if/elif/else`` : la décision repose sur des patterns de classe
    (``str()``), de mapping (``{"level": ...}``), de séquence (tuple), des
    alternatives (``|``), des captures (``as``, ``int(code)``) et des guards.
    """
    match entry:
        # 1) Chaîne brute — guard : la chaîne commence par une méthode HTTP
        case str() as raw if raw.split(" ", 1)[0] in HTTP_METHODS:
            return ROUTE_HTTP
        case str():
            return ROUTE_TEXT
        # 2) Dict d'erreur serveur : alternative "ERROR" | "CRITICAL", capture du
        #    code entier, guard code >= 500
        case {"level": "ERROR" | "CRITICAL", "code": int(code)} if code >= 500:
            return ROUTE_SERVER_ERROR
        # 2 bis) Événement de sécurité : alternatives sur le niveau ET l'événement
        case {
            "level": "ERROR" | "CRITICAL" | "WARNING",
            "event": "login_failed" | "permission_denied",
        }:
            return ROUTE_SECURITY
        # 3) Tout autre dict possédant un niveau : capture du reste (**rest)
        case {"level": str(level), **rest} if rest:
            return f"{ROUTE_EVENT}.{level.lower()}"
        # 4) Tuple de connexion (IP, Port, Protocole) — guard : port sensible
        case (str(), int(port), str()) if port in SENSITIVE_PORTS:
            return ROUTE_SENSITIVE_CONNECTION
        #    capture des 3 éléments ; guard : IP et port plausibles
        case (str(ip), int(port), str(proto)) if is_valid_ip(ip) and 0 < port < 65536:
            return f"{ROUTE_CONNECTION}.{proto.lower()}"
        # 5) Tout le reste
        case _:
            return ROUTE_UNKNOWN

                        trace.interrupted_sequences += 1
                    break  # BREAK : un login_success interrompt la séquence

                last_failure = event

            if failures >= threshold:

                            f"(cible : {start.user_id})"
                        ),
                    )
                )
                break  # BREAK : seuil atteint -> attaque confirmée, IP suivante
            index = resume
        else:
            # ELSE de la boucle WHILE : exécuté UNIQUEMENT si aucun ``break`` n'a
            # eu lieu, c.-à-d. si tous les événements de l'IP ont été analysés

    return sorted(alerts, key=lambda alert: (str(alert.start), alert.ip))

MODULE 4 — Moteur de règles et introspection¶

Les règles sont des fonctions passées en argument à apply_security_rules(*args, **kwargs). Chaque règle ne reçoit que les paramètres qu'elle déclare (inspect.signature) ; une règle qui lève une exception n'interrompt pas les autres.

Lecture. Le volume de données lu croît linéairement avec le nombre de lignes (110 Mio pour 1 million de lignes), alors que la mémoire pic du moteur reste de l'ordre du mégaoctet. Elle ne dépend que du nombre d'entités distinctes : IP, utilisateurs, heures et minutes (compteurs defaultdict, ensembles), escalades (liste plafonnée) et tampons de connexion récents — jamais de la taille du fichier. La légère hausse entre 100 000 et 1 000 000 de lignes correspond au remplissage de ces structures bornées (une journée compte au plus 1 440 minutes) : sur le fichier complet de 2 000 000 de lignes (220 Mio), python main.py benchmark --sizes ... mesure 1,96 Mio, contre 1,83 Mio à 1 million de lignes — la courbe plafonne. C'est l'effet direct des générateurs (yield / yield from) et de l'agrégation en une seule passe.

6. Limites et améliorations possibles¶

Limites

  • Ordre chronologique supposé : la détection en flux suppose des événements globalement chronologiques par IP (fichiers traités dans l'ordre). Un écart temporel négatif clôt le tampon de l'IP, ce qui reste correct mais peut couper une attaque répartie sur deux fichiers non ordonnés.
  • Une alerte par IP : dès que le seuil est atteint (break), l'analyse de l'IP s'arrête ; une seconde campagne de la même IP n'est pas rapportée séparément.
  • Règles de rafale et d'escalade : calculées sur des compteurs par minute et sur le dernier permission_denied de chaque utilisateur (approximation volontaire pour garder une mémoire bornée).
  • Mono-cœur : le débit (~15–20 000 lignes/s) est limité par le GIL et par le parsing en pur Python ; tracemalloc ralentit fortement le benchmark.
  • Formats figés : trois formats connus ; un nouveau format nécessite un nouveau case dans le routage et une branche dans parse_payload.

Améliorations

  • Lecture parallèle des fichiers (multiprocessing, un agrégateur par fichier puis fusion des defaultdict / ensembles, qui sont associatifs).
  • Mode suivi (tail -f) : le pipeline étant un générateur, il peut consommer un flux infini ; ajouter une émission périodique des alertes.
  • Fenêtre de détection paramétrable par service (SSH, RDP, HTTP…) et seuil adaptatif.
  • Export vers un SIEM (syslog, JSON lines) et signature asymétrique des rapports.
  • Configuration des règles par fichier (TOML) chargée dynamiquement dans le registre.
